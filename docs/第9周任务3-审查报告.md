# 第9周 任务3：AI 生成测试与审查

> 交付物：结构化 Prompt + AI 生成的测试代码 + 审查报告（有效性 / 边界 / 修补方案）
> 审查对象：`src/todo.ts`（任务1 产物），测试框架 Vitest 2.1.9

---

## 一、我发给 AI 的结构化 Prompt

```text
我有一段 TypeScript 代码 addTodo，业务契约如下：

1. 输入合法文本，添加任务。
2. 输入纯空格或空字符串，拒绝添加。
3. 输入超长文本，根据业务需求决定是否拦截。

请使用 Vitest 编写测试。要求按以下维度覆盖：

- 维度1（空值）：传入 null。
- 维度2（格式）：传入纯空格、空字符串。
- 维度6（重复）：连续添加相同文本。
- 维度2（格式拓展）：传入超长文本。

断言要求：必须验证具体的业务结果，不能只写 toBeDefined。
请在每个 test 上方用注释标明对应的测试维度。
```

Prompt 里写明了三件事：**契约**（什么算合法输入、什么该拒绝）、**维度**（一条一条点名，避免 AI 自己挑简单的写）、**断言强度**（明确禁止 `toBeDefined` 这类空断言）。

## 二、AI 生成的测试代码（核心片段）

```ts
import { describe, expect, it } from 'vitest';
import { addTodo, toggleTodo } from './todo';

describe('addTodo', () => {
  // 维度：正常添加
  it('正常添加一条任务', () => {
    const todos = [];
    addTodo(todos, '学习TS');
    expect(todos).toHaveLength(1);
    expect(todos[0]).toBeDefined();
  });

  // 维度2（格式）：纯空格
  it('纯空格应被拒绝', () => {
    const todos = [];
    addTodo(todos, '   ');
    expect(todos).toHaveLength(0);
  });

  // 维度2（格式）：空字符串
  it('空字符串应被拒绝', () => {
    const todos = [];
    addTodo(todos, '');
    expect(todos).toHaveLength(0);
  });

  // 维度6（重复）：连续添加相同文本
  it('重复添加相同文本', () => {
    const todos = [];
    addTodo(todos, '重复');
    addTodo(todos, '重复');
    expect(todos).toHaveLength(2);
  });
});

describe('toggleTodo', () => {
  // 维度：正常切换
  it('正常切换完成状态', () => {
    const todos = [
      { id: 1, text: '任务A', completed: false },
      { id: 2, text: '任务B', completed: true },
    ];
    toggleTodo(todos, 1);
    expect(todos[0].completed).toBe(true);
  });

  // 维度5（状态）：不存在的 ID
  it('不存在的 ID 不应抛错', () => {
    const todos = [
      { id: 1, text: '任务A', completed: false },
    ];
    expect(() => toggleTodo(todos, 999)).not.toThrow();
  });
});
```

实测结果：`npx vitest run src/ai-generated.test.ts` → **6 passed，全绿**。
同一份文件跑 `npx tsc --noEmit` → **14 处类型错误**（全部是隐式 `any[]`）。

## 三、审查报告

### ① 有效性审查：哪一句断言是无效的？

**无效断言：第 1 条用例里的 `expect(todos[0]).toBeDefined()`。**

它只验证「数组第 0 个位置上有东西」，不验证那个东西里装的是不是我传进去的文本。实现如果把文本存成空串 —— 也就是 push 进去的对象是 `{ id, text: '', completed: false }` —— `todos[0]` 依然是存在的对象，`toBeDefined()` 照样通过。这条断言连「拦住了却存成空串」都发现不了。

**实测证据（变异测试）**：把 `todo.ts` 里 `text: clean` 改成 `text: ''`（故意把文本丢掉），重新运行两套测试：

| 测试来源 | 断言 | 变异后的结果 |
|---|---|---|
| AI 生成（6 条） | 长度 / `toBeDefined` / `not.toThrow` | **6 passed，全绿，没抓到** |
| 手写断言 | `expect(todos[0]?.text).toBe('学习TS')` | **1 failed**，报错 `expected '' to be '买牛奶'` |

结论：**能跑绿的断言不等于有效断言**。判断标准只有一条 —— 把实现改错，它会不会变红。`toBeDefined` 不会，所以它是无效断言。

**另外还有一处更隐蔽的问题，不是断言强弱，而是类型层面违规：**

AI 生成的所有用例都写 `const todos = []`，没有标注类型。在 `strict: true` 下这推导出隐式 `any[]`，`npx tsc --noEmit` 报出 14 处 `TS7034` / `TS7005`。而 `npm run test` 显示 6 条全绿 —— 因为 **Vitest 只用 esbuild 转译，不做类型检查**。

这一处最值得记录：它同时证明了两个结论 —— AI 的输出没有遵守任务1 的三条红线（严禁 `any`），以及「测试通过」根本不能作为「代码合格」的证据。

### ② 边界审查：对照 9 维度查漏

| # | 维度 | AI 是否覆盖 | 判定 |
|---|---|---|---|
| 1 | 空值 | 没写 | 见下方说明 |
| 2 | 格式（空格 / 空串） | 覆盖 | 保留 |
| 2 | 格式拓展（超长文本） | **没写** | **要补** |
| 3 | 类型 | — | 由 TS 签名 + tsc 保证 |
| 4 | 越界 | — | 本模块无按下标访问 |
| 5 | 状态 | 只测了单向翻转 | **要补** |
| 6 | 重复 | 覆盖 | 保留 |
| 7 | 异步 | — | 全部同步函数，不适用 |
| 8 | 依赖 | — | 不依赖 localStorage / 网络，不适用 |
| 9 | 安全 | — | 纯内存函数，不适用 |

对照后，**当前业务真正需要补的是两处**：

1. **维度2 格式拓展 —— 超长文本。** 契约第 3 条写的是「根据业务需求决定是否拦截」。当前实现不设长度上限，所以正确预期是**原样入库、不被截断**。AI 完全没写这条。
2. **维度5 状态 —— 连续切换。** AI 只验证了「翻一次变成 true」。如果实现写成 `target.completed = true`（忘了取反），这条用例照样通过，因为初始值就是 `false`。必须补一条「连续切换两次回到 `false`」才能把「取反」这个语义钉住。

关于**维度1（空值 null）**的处理：Prompt 里点名要求传 null，但 `addTodo` 的签名是 `text: string`，strict 模式下编译期就禁止传 null；运行时真要测只能写 `null as any`，这直接违反任务1 的三条红线（严禁 `any`、严禁 `as`）。所以这一维我选择由**类型系统 + `tsc --noEmit` 覆盖**，不写运行时用例 —— 由编译器挡在编译期，比在运行时补一条用例更彻底。这也解释了为什么 AI 会「悄悄漏掉维度1」：它如果照 Prompt 写，代码要么类型不通过，要么得用 `as any` 破坏约束，于是它干脆跳过了。

### ③ 我的修补方案

针对上面两处空缺和三处弱断言，手写修补如下：

```ts
import { describe, expect, it } from 'vitest';
import { addTodo, toggleTodo } from './todo';
import type { Todo } from './todo';

describe('addTodo · 人工修补', () => {
  // 修补①：显式标注 Todo[]，消除 AI 输出里的隐式 any[]
  // 修补②：断言具体文本，替换无效的 toBeDefined
  it('正常添加：入库内容与输入一致', () => {
    const todos: Todo[] = [];
    addTodo(todos, '学习TS');
    expect(todos).toHaveLength(1);
    expect(todos[0]?.text).toBe('学习TS');
  });

  // 修补③：补维度2（格式拓展）—— 超长文本当前业务不拦截，应原样入库
  it('超长文本：不截断，原样入库', () => {
    const todos: Todo[] = [];
    addTodo(todos, 'x'.repeat(5000));
    expect(todos).toHaveLength(1);
    expect(todos[0]?.text).toHaveLength(5000);
  });
});

describe('toggleTodo · 人工修补', () => {
  // 修补④：把 id=2 的初始值改成 false，断言才不是「初始值等于期望值」
  it('切换目标：只有目标翻转，其他条目不变', () => {
    const todos: Todo[] = [
      { id: 1, text: '任务A', completed: false },
      { id: 2, text: '任务B', completed: false },
    ];
    toggleTodo(todos, 1);
    expect(todos[0]?.completed).toBe(true);
    expect(todos[1]?.completed).toBe(false);
  });

  // 修补⑤：补维度5（状态）—— 连续切换两次应回到原状态
  it('连续切换两次：回到初始状态', () => {
    const todos: Todo[] = [{ id: 1, text: '任务A', completed: false }];
    toggleTodo(todos, 1);
    toggleTodo(todos, 1);
    expect(todos[0]?.completed).toBe(false);
  });

  // 修补⑥：AI 只写了 not.toThrow，补上「数据未被改动」的断言
  it('不存在的 ID：不抛错且数据不变', () => {
    const todos: Todo[] = [{ id: 1, text: '任务A', completed: false }];
    expect(() => toggleTodo(todos, 999)).not.toThrow();
    expect(todos).toHaveLength(1);
    expect(todos[0]?.completed).toBe(false);
  });
});
```

修补后验证：

| 实现状态 | AI 原版（6 条） | 修补版（5 条） |
|---|---|---|
| 正确实现 | 6 passed | 5 passed |
| 变异A：`text` 存成空串 | **6 passed（漏）** | **2 failed（抓到）** |
| 变异B：`toggle` 写死 `= true` | **6 passed（漏）** | **1 failed（抓到）** |

两处变异都验证了同一件事：修补版能被改坏，AI 原版不能。这就是「改坏了会红」的实际含义。

---

## 四、一句话总结

用结构化 Prompt 能把 AI 的产出框在契约和维度里，但**它框不住断言强度**——同一次生成里有 6 条用例全绿，却对「文本存成空串」和「切换写死 true」两种明显错误毫无反应；真正让测试变可信的不是 AI，是我把它改坏之后看它红不红。
